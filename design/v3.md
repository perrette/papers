# papers v3: design

This file describes the model of papers v3 and the reasons for its main
decisions. The user documentation (docs/) describes the commands; it is not
repeated here.

## Libraries

A library is a bibtex file, a files directory and a configuration file next
to the bibtex (`.papersconfig.json`). It is the only unit: one library per
project. Commands act on the library found in the current directory or
above (`-C DIR` changes the directory, as in git); outside of any library,
on the global pool once it is a library.

Version 2 had a global configuration that defined a library for the whole
user account, and local configurations that overrode it. Two kinds of
configuration with different rules made it hard to tell which library a
command acted on. In v3 the global configuration (`papers config --global`)
defines no library: it holds the global pool and the defaults of the
settings that a library does not set. Each setting comes from the library,
else the global configuration, else a built-in default; `papers config`
shows which.

`papers init` creates a library and asks no questions; settings change with
`papers config`. `papers init` stores the settings that determine the
content of the library (`paths`, `git`, `local`, and `pool` when it is not
the global pool), so that changing a default later does not change existing
libraries. Paths in the library configuration are relative to the library,
and the backup directory is stored by name, so that a library folder can be
moved or copied to another machine.

The configuration files written by v3 carry `"version": 3`. A file without
version is a file of v2: its library configurations need no migration (they
are local libraries that use the global pool), and `papers migrate` turns
the v2 global configuration into a library (the global pool).

## Pools

Many projects cite the same papers, and the corrections made to an entry in
one project (a page range, a journal name) are useful in the others. A pool
is a library that libraries exchange entries with. Any library can be a
pool; nothing in it marks it as one.

A library has one pool, its `pool` setting:

- by default the global pool, the `pool` setting of the global
  configuration (`~/Documents/papers` without one). A library that uses it
  stores no path, so that a project copied to another machine uses the
  global pool of that machine, wherever it is there;
- a path, stored relative to the library when given relative or under the
  library, so that a folder shared with someone (`../shared-with-bob`) moves
  with the projects;
- `none`.

Earlier v3 builds had a list of pools per library and pool names in the
global configuration. One pool is enough: the cases that needed several
pools (pulling once from a colleague's folder, pushing once to it) are
`pull --pool PATH` and `push --pool PATH`, and the portability that names
gave is that of the global pool. A list of pools also made the outcome of
`pull` and `add` depend on an order (the first pool that has the paper),
and left open where `push` and new files go.

The global pool may not exist. It is created, without a message, the first
time papers writes to it, so that a new user can start with `papers init`
and `papers add` without setting anything up; before that, reading from it
finds nothing. A missing pool given by path is a warning instead, since it
is more likely a typo or a disk that is not mounted, and papers only creates
it if its parent directory exists.

Nothing is pulled automatically: an older project does not change because of
work in a newer one. `status` and `pull --check` tell that the pool changed
since the last exchange with it (pull, push or add; a modification time check, no merge). Pushing is
automatic only where the pool must have the entry (below), and with the
`auto-push` setting in a local library (new entries only, never changes to
existing ones).

## Local or not

A paper used by several projects should be stored once. `local: false`
(the default for new libraries) keeps the files of a library in the files
directory of its pool: `add` places the PDF there, with the pool's name
template, and adds the entry to the pool too, since the pool needs the entry
of its file; `pull` links to the pool's files. `local: true` keeps the files
in the library's own files directory, as in v2; a library without pool is
local.

A library that is not local depends on its pool: its links point into it.
That is why a project folder shared with others (git, Dropbox) must be
local, and why `export` writes a local library without pool: it is meant to
be handed over. When the pool renames a file, the links break; they are
repaired from the pool entry when the library is loaded and by
`file check --fix`. The pool keeps no list of the libraries that use it.

Changing `local` or `pool` moves files, so `papers config` lists what it
will do and asks before doing it (`-y`, `--dry-run`; without a terminal it
stops). The rules come from one constraint: never delete a file that is not
safely in a pool, and never delete a file of a pool, since other projects
may link to it. Going local copies the pool files (hard links when
possible). Going non-local moves the library's own files into the pool; a
file that the pool already has with the same content becomes a link to the
pool's copy, and only then is the library's copy deleted. Changing the pool
of a non-local library copies the files of the former pool. These commands
move files only: merging metadata is the job of `push`, with its dialogue.

Earlier v3 builds called these "full" and "light" libraries, changed with
`papers migrate --light/--full`. A setting named after where the files are
reads more plainly, and `papers config` is where settings change.

## Identity of an entry

Two entries are the same paper when they share an identifier, checked in
order: DOI, arXiv identifier, ISBN (two books only), otherwise the family
names of the authors and the title. The first identifier both have decides.
This one rule (`papers.duplicate.same_paper`) is used by `add`, `check
--duplicates`, `list --duplicates`, `pull` and `push`. Version 2 had five
similarity levels (`--similarity`), which gave different answers to the same
question in different commands; fuzzy matching remains only for searching
(`list --fuzzy`, `list --duplicates --fuzzy`), where a wrong match costs
nothing.

Some details of the rule have reasons the user docs do not give:

- ISBNs count only for two books, because a chapter carries the ISBN of its
  book;
- equal identifiers with different entry types and different titles are
  asked about rather than merged: a chapter exported with its book's DOI, a
  dataset deposited under its article's DOI. Same type and same DOI is the
  same paper whatever the titles, since titles are often abbreviated;
- the pairs answered "not the same paper" are stored by identifiers, not
  keys (`.papers/distinct.json`), so that the file means the same in every
  library and can be merged between a library and its pool;
- without a terminal, a conflict stops the command (`--on-duplicate error`)
  rather than choosing a side silently.

## Keys

The key belongs to each library: it is what LaTeX documents cite. `pull`
and `push` never change the key of an entry of the library they write to.
An entry new to the pool gets a key from the pool's key template; an entry
of the pool new to the library keeps the pool key, with a letter suffix if
the library has it already. Since nothing matches on keys, a pool may
regenerate its keys freely.

## Origin copies and three-way merge

`.papers/origin.bib` of a library records, for each entry taken from or
given to a pool, the base of the next merge, under the library's key, with
the pool (`global` for the global pool, so that the record holds on
another machine; otherwise its path relative to the library) and the pool
key. The base is the version that the sending side sent: the pool entry
after `add` and `pull`, the library entry after `push`. The receiving side
has taken all of it into account (taken, kept or declined), so the base is
a version that both sides have seen, and what the receiver has beyond it is
its own change, for the next exchange the other way. Recording the merged
pool entry after a push would hide the fields that only the pool has (the
next pull would see them as removed in the library), and a later push would
take back a pool change made before the first push. The base is used for a
three-way merge: a field changed in the pool only
is taken, a field changed in the library only (e.g. adapted to a journal
style) is kept without asking, a field changed on both sides is a conflict,
decided with the dialogue of the duplicate check. Without a base, every
difference would be a conflict, and a library could not keep its own
adaptations of an entry across pulls.

This is the difference between `papers add other.bib` and `papers pull`:
`add` copies entries once, with no memory of the source; entries taken by
`pull` stay linked to the pool through their origin copy, and later pulls
bring the corrections made there. `papers sync` is `pull` then `push`, and
stops before pushing when the pull leaves conflicts undecided, so that a
skipped conflict is not overwritten in the pool.

## Files

What `add` does with a file is the `files` setting: `move` (default, for
PDFs taken from a downloads folder), `copy` (a hard link when possible) or
`link` (the entry links to the file where it is). A file that belongs to
another library, or to the pool, is never moved, so that the other library
keeps its link.

The files directory is flat: each file is named after the name template of
the library that holds it (the pool's template for the files in the pool).
Version 2 before 2.19 kept the files of an entry in a folder of their own
with a hidden bibtex; `papers migrate --folders` moves them, and `add`
still reads such folders.

The git backup of a library lives in the backup folder of the machine, not
in the library, so that the library folder holds only the bibliography and
its files. The libraries of papers 2.2 to 2.4 kept it in `.papers/`, now the
folder of `origin.bib` and `distinct.json`: the first backup moves it out.

## Command line

The command line follows git where it can: `init`, `config` (`--global`,
`--unset`), `status`, `-C DIR`, `pull`, `push`, `rm`, `file mv`. Each option
keeps one meaning across commands (`-a` is `--author`, `-f` is `--force`,
`-y` is `--yes`, `-R` is `--recursive`), file actions are subcommands of
`papers file`, and entry actions have their own commands (`edit`, `rm`,
`tag`) besides the shortcuts of `list`. Commands that act on entries take
any identifier: key, former key (`ids`), DOI, arXiv id or ISBN, or `-` for
the standard input.

The forms of v2 keep working in v3 with a deprecation warning that prints
the new form, and are removed in v4.

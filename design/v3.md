# papers v3: design (draft for discussion)

Status: under discussion, nothing implemented. Development happens on the
`v3` branch; v3 is a major version because it changes the configuration
model and the command set.

## 1. Data model

### Libraries and pools

- A **library** is a bibtex file, an optional files folder, and a
  configuration file next to the bibtex (`.papersconfig.json`). This is what
  `papers install --local` creates today, and it remains the basic unit: one
  library per project, with its own bib and, by default, its own files.
- A **pool** is an ordinary library that other libraries exchange entries
  with. Nothing in the pool itself marks it as a pool: a library acts as a
  pool when another library lists it in its `pools`. Any existing library
  can therefore serve as a pool.
- Several pools are kept fully separate by being separate folders (e.g. one
  per research field). A project names the pools it uses.

### Configuration

```
~/.config/papers/config.json          # per machine (platformdirs location)
{"pools": {"default": "~/Documents/papers", "teaching": "/mnt/shared/teaching"}}

projectA/.papersconfig.json           # per library
{"bibtex": "refs.bib", "filesdir": "files", "pools": ["default", "../shared-with-bob"]}
```

- `pools` lists names or paths. A name is looked up in the per-machine
  configuration, so the same project works on machines where the pool is in
  a different place. A path is relative to the library (useful for a folder
  shared with someone).
- `pull` searches the pools in order; `push` writes to the first one.
- Without per-machine configuration, `default` is `~/Documents/papers`,
  created the first time something is pushed to it. A library created
  without `--pool` gets `"pools": ["default"]`.
- The per-machine configuration only holds pool names and user preferences
  (editor...). It no longer defines a library.

### Local versus global

The global install goes away:

- Inside a library (a configuration file found in the current directory or
  above), commands act on that library.
- Outside any library, commands act on the default pool.
- Migration: an existing global configuration is registered as the
  `default` pool (its bibtex and files directory stay where they are).
  Existing local configurations keep working.

### Identity of an entry

- Two entries are the same paper when their DOIs are equal or, when one of
  them has no DOI, when their author and title match. This is the rule of
  the duplicate check today (`PARTIAL`, the default level).
- The key belongs to each library. It is what LaTeX documents cite, so
  `pull` and `push` never change the key of the library they write to. A
  pool's keys may be regenerated freely, because nothing matches on them.
- Duplicate check simplification: the five levels
  (`EXACT/GOOD/FAIR/PARTIAL/FUZZY`, option `--similarity`) are reduced to
  "same paper" (the rule above, used by add, check, pull, push) and "fuzzy"
  (for searching only, `list --duplicates --fuzzy`).

### Origin copies and three-way merge

- `.papers/origin.bib` in a library stores, for each entry taken from a
  pool, the pool's version of the entry at the time it was taken (or last
  pulled), under the library's own key, with the pool it came from.
- To find the pool entry of a library entry, papers matches the origin copy
  in the pool with the identity rule above.
- `papers pull` compares three versions field by field:
  - changed in the pool only: offer the update;
  - changed in the library only (e.g. a field adapted to a journal style):
    keep it, without asking;
  - changed in both: ask, using the existing merge dialogue of the
    duplicate check.
- After a pull, the origin copy is updated. `papers push` does the same in
  the other direction.
- Nothing is pulled or pushed automatically: an older project never changes
  because of work in a newer one.

### Files

- Taking an entry from a pool copies its files into the library's files
  folder: hard link when on the same file system, copy otherwise.
- A **light** library has no files of its own: its file links point into
  the files of its first pool. Light is a setting of the library, because
  it changes later behaviour:
  - `add` places new PDFs in the pool (and so adds the entry to the pool
    too, since the pool needs the entry for its file);
  - `pull` links to the pool's files instead of copying them.
- Switching a library to light (`papers migrate --light`, see section 3)
  converts its existing files: each file that
  the pool has for the same paper (same content, by checksum) is replaced
  by a link to the pool's file, and the library's copy is deleted. A file
  that is not in the pool is not deleted: the command lists those entries
  and asks to `papers push` them first. Switching back copies (or hard
  links) the pool's files into the library's files folder.
- When a pool renames a file, the links of light libraries break. They are
  repaired by looking the entry up in the pools (on `filecheck`, or when a
  broken link is found on load; the repair is saved on the next write). The
  pool keeps no list of the libraries that depend on it.
- Known risk: deleting a file in a pool breaks the light libraries that link
  to it. It shows up as a broken link in those libraries.

### What `add` does with a file

Two actions underlie `add -r` today: (a) place the file in the files folder
under its template name, and (b) remove the source. A library setting
chooses between them, with a per-machine default and a command-line
override:

- `files: move` (default): (a) + (b); what `add -r` does today, and suited
  to adding PDFs from a downloads folder;
- `files: copy`: (a) only, with a hard link when possible, otherwise a copy;
- `files: link`: neither; the entry links to the file where it is (what
  `add` does today without `-r`).

Options: `--move`, `--copy`, `--link`. A file that already belongs to
another library (inside its files folder, or linked from its bibtex) is
never moved: `move` falls back to `copy` for it, so that the other library
keeps its link. In a light library, (a) places the file in the pool.

There is no separate `import` command: `add` is the import. `add DIR` reads
the bibtex files of the folder first and takes their entries and files
from them (2.19.1), so `add` of a folder made by `export` restores it.

### Name and key templates

- The name template belongs to the library that holds the files in its
  files folder. A full library uses its own; a light library uses its
  first pool's (a name template set on a light library is ignored, with a
  warning).
- `pull` into a full library names the copied or hard-linked file with the
  receiving library's template; `push` names it with the pool's template.
- The key template is always per library, since keys belong to each
  library: a pool may regenerate its keys with its own template, a project
  keeps its keys.
- Resolution order for both: library configuration, then per-machine
  configuration, then built-in default.

### Turning an existing library into a pool

`papers export --pool new/path` copies the bibtex and the files (hard links
when possible) into a new library and adds it to the current library's
pools.

Options shared by all library commands: `--bibtex`, `--filesdir`,
`--dry-run`, `--relative-paths`, `--absolute-paths`, `--no-git`, logging
levels; name and key format options on `install`, `add`, `filecheck`,
`check` (key only).

### Inconsistencies found

1. **Same short option, different meaning:** `-a` is `--attachment` in
   `add` and `--author` in `list`; `-f` is `--force` in `check`/`backup` and
   `--field` in `list`; `-m/--mode` has different choices in `add` and
   `check`.
2. **`--force` means different things:** in `install` it means no prompt;
   in `filecheck` no prompt and follow options; in `backup` no confirmation.
3. **`--edit`:** in `add`/`list` it opens entries in an editor; in
   `install` it means "update without prompting".
4. **`--recursive`:** scans directories in `add`/`extract`, but removes
   configurations up the directory tree in `uninstall`.
5. **Renaming exists in three places** (`add -r`, `filecheck -r`,
   `list --rename`), with short options in two of them.
6. **Duplicates in two places:** `check --duplicates` (resolve) and
   `list --duplicates*` (show), with five similarity levels exposed.
7. **`filecheck` mixes checks and actions:** `--metadata-check`,
   `--hash-check`, `--delete-broken`, `--clean-filesdir`, `--fix-mendeley`,
   `--rename`.
8. **Three lookup commands:** `doi` (DOI of a PDF), `extract` (metadata of
   a PDF), `fetch` (bibtex of a DOI or text); `doi` is a subset of
   `extract`.
9. **Two names for git backup:** `--git`/`--backup`,
   `--git-lfs`/`--backup-files`, plus a `backup` command and a `git`
   command.
10. **`--relative-paths`/`--absolute-paths` on every command**, although
    this is a property of the library.
11. **Help text errors:** `--key-title-word-size` says "number of title
    words"; the `(default: ...` of `--filesdir`/`--bibtex` is not closed.

## 3. Proposed v3 command set (to be decided)

| Command | Change |
|---|---|
| `init` | replaces `install` (kept as an alias); creates a library only: `--pool NAME|PATH...`, `--light`; no `--local`/`--global` |
| `config` | new: `papers config` shows the settings, `papers config KEY VALUE` sets one (pools, files mode, templates, editor, git...); replaces `install --edit` and re-running `install` |
| `migrate` | new: changes that involve the bibtex links, the files and the configuration together: `--light` / `--full`, and one-time upgrades from v2 (global configuration → `default` pool; pre-2.19 folders → flat layout) |
| `status` | also shows pools, files mode, and whether the library is light |
| `add` | looks in the pools first (same paper → taken from the pool, no fetching); `--move`/`--copy`/`--link` |
| `pull`, `push` | new: three-way merge with the pools |
| `export --pool PATH` | new: make a pool from the current library |
| `pool` | new: `list`, `add NAME PATH`, `remove NAME` in the per-machine configuration |
| `file` | replaces `filecheck` and the file actions of `list`: subcommands `rename`, `mv`, `add`, `rm`, `check`, `clean` (below) |
| `list`, `open`, `check` | kept; options to be harmonized (section 2) |
| `fetch`, `extract` | `doi` folded into `extract --doi-only` |
| `undo`, `redo`, `restore` | `restore-backup` renamed `restore` |
| `git`, `backup` | kept |

Decided:

- New entries reach a pool only through `push`, unless the library sets
  `sync: true` (then `add` also adds new entries to the first pool). Edits
  are never pushed automatically.
- Settings are changed with `config`, not `init`.
- `light` cannot be changed with `config`: it changes links and files, so
  it is changed with `migrate --light` / `--full`, which refuses entries
  whose files are not in the pool (run `papers push` first) and never
  deletes a file that is not in the pool.

- `sync: push` (default `none`): `add` also adds new entries to the first
  pool. There is no automatic pull and no `sync` command; `status` and
  `pull --check` report that a pool changed since the last pull (a
  modification time check, no merge).
- Default files mode: `move`. Settings command: git-style
  `papers config [KEY [VALUE]]`. File paths are relative to the bibtex by
  default.

### Selecting entries and piping

- Commands that act on entries take keys or DOIs (a DOI starts with `10.`;
  keys cannot start with a digit), and `-` reads them from the standard
  input, one per line: `papers list smith 2020 -K | papers file rename -`.
- `list` gets `-K` for `--key-only` (`-k` stays "search by key").
- An action stays on `list` only if no dedicated command does it.
  `--rename`, `--copy`, `--add-files`, `--open`, `--fetch` move to
  `file rename`, `file add`, `open`, `check --fetch`; in v3 they still work
  with a deprecation warning that shows the new form, and are removed in v4.
  `--edit`, `--delete`, `--add-keywords` stay for now (the command review
  decides whether they become `edit`, `rm`, `tag`).

### `papers file` subcommands

| v3 | Today |
|---|---|
| `file rename [KEY|DOI...]` (`--keep-source`) | `filecheck -r [-c]`, `list --rename [--copy]` |
| `file mv SRC... DEST` | `filecheck --rename --filesdir NEW` (which also renames) |
| `file add KEY FILE...` | `list --add-files` |
| `file rm KEY [FILE...]` (`--broken`, `--delete`) | `filecheck -d` |
| `file check [KEY...]` (`--fix`) | `filecheck`, `--hash-check`, `--metadata-check`, `--fix-mendeley` |
| `file clean` | `filecheck --clean-filesdir` |

`file mv` works like `mv` and follows the rules of `git mv`, and also
updates the entries that link to the moved files:

1. a source file that no entry links to is an error, and nothing is moved;
2. a source folder must contain at least one linked file; the whole folder
   moves, files no entry links to included;
3. with several sources, the destination must be an existing folder;
4. a destination that exists as a file is an error, unless `-f/--force`;
5. `-n/--dry-run` shows the moves and the entries that change;
6. moving the library's files folder also updates `filesdir`.

All checks run before anything moves. If a move fails midway, the bibtex
is saved with the links of the files already moved. Links from other
libraries break (pool files are found again through the pools; papers
cannot know about other links).

`export DIR [KEY...] [--files copy|link|none] [--pool]` stays a top-level
command: it creates a library (bibtex, files, configuration) rather than
moving files.

Open questions:

1. Do `--edit`, `--delete`, `--add-keywords` of `list` become commands of
   their own (`edit`, `rm`, `tag`)?
2. The full command review (section 2 inconsistencies) before any name is
   fixed.
